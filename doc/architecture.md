
`OnnxMarianEngine` is the **only** class that knows about ONNX Runtime, and the
`native/` directory is the only place that touches `dart:ffi`. Everything above
`TranslationEngine` was untouched when the backend was replaced, which is what
that interface exists for. See [onnx-runtime.md](onnx-runtime.md).

`OnnxMarianEngine` is the **only** file that imports `package:onnxruntime`.
Everything above it talks to `TranslationEngine`, which is what makes the
backend replaceable — and what lets the whole orchestration layer be unit-tested
against a fake engine with no native code involved.

## Translating a short text

```text
translateSync("Hello, how are you?")
        │
        ├─ cache hit? ──────────────────► TranslationResult(fromCache: true)
        │
        ├─ model loaded? ── no ─────────► throw ModelNotLoadedException
        │
        ├─ TextSegmenter.split          (1 chunk, it fits)
        │
        └─ per chunk:
             MarianTokenizer.encode
                  normalize (nmt_nfkc, charsmap trie)
                  Viterbi over 32 000 unigram pieces
                  pieces → ids via vocab.json, append </s>
             ONNX encoder    → last_hidden_state
             ONNX decoder    → greedy loop (below)
             MarianTokenizer.decode
```

The synchronous path never awaits. It is one Dart call chain into FFI and back,
which is why `translateSync` can return a `TranslationResult` rather than a
`Future`.

## The greedy loop

```text
step 0:  input_ids = [decoder_start]         use_cache_branch = false
         past_kv    = 24 empty tensors
             │
             ├── next_token                   int64, one value
             ├── present.*.decoder.*  ──┐     self-attention KV
             └── present.*.encoder.*  ──┼──►  cross-attention KV, captured once
                                        │
step n:  input_ids = [previous token]   │     use_cache_branch = true
         past_kv    = decoder KV from step n-1
                    + encoder KV from step 0 ─┘
             │
             ├── next_token
             └── present.*.decoder.*          (encoder outputs are empty here)

stop when next_token == eos, or the length limit is hit
```

Three details make this fast and cheap across the FFI boundary:

**1. The arg-max lives in the graph.** `tool/build_model.py` appends
`ArgMax(logits + bad_words_mask)` as a `next_token` output. The engine requests
only `next_token` and the KV tensors, so ONNX Runtime never materialises the
`[1, 1, 59514]` logits tensor for Dart. One `int64` per token crosses the
boundary instead of 238 KB.

**2. KV tensors never enter Dart.** A run returns `OrtValue` handles wrapping
native pointers. Those handles are bound straight back as the next step's
inputs. The 6 layers × 2 tensors of self-attention cache are copied zero times.

**2b. A step allocates nothing at all.** An `OrtRunPlan` pre-encodes one call
signature — input names, input values, output names, output values — as native
arrays owned by the session. Running it writes pointers into those arrays
instead of building them. `input_ids`, the two `use_cache_branch` flags and the
24 first-step placeholders are created once at load and rewritten in place; the
encoder's buffers are allocated once at full width and re-viewed per input
length. This is what removed the previous binding's ~1 KB-per-token native
leak.

**3. Cross-attention KV is computed once.** The merged decoder only emits real
`present.*.encoder.*` on the first step; on cached steps they are empty
placeholders. Feeding those back throws inside the graph, so the engine captures
them at step 0 and reuses them unchanged.

Generation stops on `eos`, on `maxNewTokens`, or on
`lengthRatioLimit × input_length + 8` — the last one is the guard against the
degenerate repetition loops that greedy decoding can fall into.

## Two isolates, one model

```text
UI isolate                                worker isolate
──────────                                ──────────────
OrtEnv, encoder, decoder  ─── addresses ─▶ adopted, non-owning
MarianRunner                               MarianRunner (its own plans,
  plans, scratch tensors                     scratch tensors, tokenizer)
  MarianTokenizer
     │                                          │
translateSync() ───────────────────────────────┘  (never used here)
translate()        ── chunks ─────────────────▶ generate
translateStream()  ◀── translated chunks ──────
```

ONNX Runtime sessions are safe to call `Run` on from several threads, so the
worker attaches to the sessions already resident rather than loading a second
copy. **The model is loaded once**; the worker adds only its own run plans,
scratch tensors and a tokenizer copy.

That split is what lets both APIs be honest at the same time:

* `translateSync()` runs on the caller's isolate, returns a `TranslationResult`
  rather than a `Future`, and blocks — measured at 1.1-1.5 s for 100 words,
  which is why it is documented for sentences.
* `translate()` and `translateStream()` hand their chunks to the worker. During
  a 15 000-character document the calling isolate kept an 8 ms timer running
  with a worst gap of 40 ms (macOS) to 116 ms (4-core Android emulator).

If the isolate cannot be spawned, the engine falls back to translating on the
calling isolate and yielding between chunks: slower to the eye, never wrong.

## Long text

```text
"…several paragraphs…"
        │
        ├─ split on paragraph breaks
        │     └─ each block over budget?
        │           ├─ split on sentence endings  (. ! ? … 。 ！ ？ + closing quotes)
        │           ├─ still over? split on clauses  (, ; : — –)
        │           ├─ still over? split on words
        │           └─ still over? fixed 120-character slices
        │
        ├─ greedily pack pieces up to maxInputTokens, measured with the real tokenizer
        │
        ├─ translate each chunk
        │     └─ translate() awaits Future.delayed(Duration.zero) between chunks
        │
        └─ reassemble: every chunk carries the whitespace that followed it,
           so "A.\n\nB." comes back as "A'.\n\nB'."
```

Chunk budgets are measured with `engine.encodeText(s).length` — the real
tokenizer, not a character heuristic — so a chunk is always guaranteed to fit
the encoder.

`translateStream` yields one `TranslationResult` per chunk, with the separator
already appended, so concatenating the stream reproduces exactly what
`translate` returns. That equivalence is asserted in the integration tests.

## Model lifecycle

```text
                    installModel()               (network, once)
                          │
                    ┌─────▼──────┐
                    │  on disk   │  <app support>/offline_translator/models/en-fr
                    └─────┬──────┘
      preload() /         │        deleteModel()
      first translate()   │             │
                    ┌─────▼──────┐      │
                    │ in memory  │      │
                    │  (engine)  │      │
                    └─────┬──────┘      │
        unload() / LRU    │             │
        eviction /        │             │
        dispose()         ▼             ▼
                       released      removed
```

Loading is what costs (570-1 140 ms and 180-350 MB), so a loaded engine stays
resident and is reused. `OfflineTranslator` keeps a `Map` ordered
least-recently-used first and evicts past `maxLoadedModels` (default 2).
Concurrent requests for the same direction share one in-flight load through a
`_loading` map, so three simultaneous `translate()` calls trigger one load.

Installation is atomic. Files download into `<pair>.tmp`, every one is checked
against its SHA-256, and only then is the directory renamed into place. An
interrupted or corrupted install therefore cannot leave a half-written model
that fails later at inference time — the existing model, if any, stays intact.

## The tokenizer

Three ported pieces, all pure Dart, all synchronous:

| file | what it is |
|---|---|
| `spm_model.dart` | minimal `sentencepiece.ModelProto` reader — pieces, scores, types, and the `precompiled_charsmap` blob |
| `spm_normalizer.dart` | `nmt_nfkc` normalisation: a darts-clone double-array trie walked over UTF-8 bytes, exactly as `Normalizer::Normalize` does |
| `unigram_model.dart` | Viterbi segmentation, a port of `Model::EncodeOptimized`, plus the unknown-run merging that `SentencePieceProcessor` applies afterwards |
| `marian_tokenizer.dart` | piece ↔ id through `vocab.json`, `</s>` suffix, `>>xx<<` prefixes |

They consume the **unmodified upstream `source.spm` and `vocab.json`**, so a
bundle can be audited against Hugging Face checksums, and correctness is pinned
by comparing against `transformers.MarianTokenizer` and `sentencepiece` over
1 822 cases including 300 uniformly random Unicode strings. See
[technical-decision.md](technical-decision.md) §3.

Two details in there are easy to get subtly wrong and were both caught by the
comparison: scores must accumulate in **32-bit** precision (otherwise near-ties
resolve differently), and consecutive unknown pieces must be **merged** into one
(otherwise a ZWJ emoji sequence becomes seven `<unk>` instead of one).

## Extension points

| To change… | Implement | Notes |
|---|---|---|
| the inference backend | `TranslationEngine` | pass through `engineFactory` |
| where models come from | `ModelSource` | HTTP and directory sources ship |
| how models are stored | `ModelManager` | `FileModelManager` is the default |
| chunking policy | reuse `TextSegmenter` with a different budget | `GenerationConfig.maxInputTokens` |
| caching policy | `TranslationCache` | optional; off by default |

Two things are deliberately *not* extension points yet, and both would change
the public API if added carelessly:

* **Language auto-detection.** `translate()` takes explicit `from`/`to`. Adding
  `autoDetect: true` means adding a detector — a small character n-gram model
  over four languages would be a few hundred kilobytes — and having
  `_resolvePair` consult it. Nothing in the current design blocks it.
* **Beam search.** `GenerationConfig` is the place for it, and the engine's
  greedy loop would grow a beam dimension. The in-graph arg-max would need to
  become a top-k output. See [technical-decision.md](technical-decision.md) §4.2
  for why greedy was chosen for V1.
